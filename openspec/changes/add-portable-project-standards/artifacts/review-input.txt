# Project Standards

Use this skill when a workflow slice needs project or technology rules for
implementation or review. It supplies a selection method and portable
references; it does not replace the target project's documentation, tooling, or
executable checks.

## Precedence And Sources

Apply rules in this order:

1. The user's explicit instruction and the target platform's requirements.
2. The target repository's `AGENTS.md`, contribution guide, architecture notes,
   specs, and accepted decisions.
3. A relevant reference from this skill.
4. Generic workflow defaults.

Read the project's manifests and configuration before choosing a reference:
language and runtime version, framework, data-access library, compiler and
formatter settings, test commands, and migration tooling. The repository's
written rules and checks win over a reference example. When a source is missing,
conflicting, or unreadable, report the gap; do not invent a rule or claim the
standards were loaded. Never copy private project code or identifiers into a
shared skill.

## Select only what applies

1. Derive the actual change surfaces from the acceptance criteria: language,
   framework, persistence layer, UI, infrastructure, and test environment.
2. Always read `references/common.md`.
3. Read `references/java.md` only for JVM work.
4. Read `references/spring-mybatis-plus.md` only when the project already uses
   Spring and MyBatis-Plus. Do not introduce JPA, an extra repository layer, or a
   new persistence framework to satisfy a reference.
5. Go, Rust, Python, and Vue have no detailed reference in this first phase.
   Use the target project's conventions and tooling for them, and state that this
   skill adds no stack-specific rules.
6. Do not load every reference by default. Record which sources and revisions
   were selected, or mark the selection as incomplete.

## Produce A Bounded Standards Brief

Before dispatching implementation or review, turn the selection into a short
brief for the handoff:

- Inline the rules that apply to this slice; do not make a fresh child read a
  whole reference to recover them.
- Give absolute paths to any file the child must open for new information.
- Name project overrides and the evidence that proves them (config keys,
  dependency versions, scripts).
- Name the verification commands and the database evidence the slice requires.
- Separate required rules from suggestions, and mark unknown facts as
  `UNVERIFIED`.

A fresh child may not inherit the parent's project or skill context, so the brief
must stand alone. Keep it proportional to the slice; a path list alone is not a
brief.

## Apply In The Workflow

- **Plan:** add the selected brief to the slice context package, test seam, and
  verification plan.
- **Implement:** follow the selected rules and report deliberate deviations with
  their reason and evidence.
- **Review:** check the same selected rules under the existing Standards axis;
  do not create a separate review, model route, or additional review round.

## Limits

This skill adds no scheduler, agent role, model choice, coverage quota, or
independent review gate. It does not authorize blanket database locks, global
plugins, or project-wide migrations. If project rules conflict with a reference,
follow the project and surface the conflict; never weaken correctness, security,
accessibility, or required verification to match a generic rule.

# Common Project Standards

This reference covers rules that apply regardless of stack. It is deliberately
small; project documentation replaces it wherever they differ.

## Discover Before Deciding

- Read `AGENTS.md`, contribution guidance, and the nearest project instructions.
- Read build and dependency manifests before assuming a language version, a

  Do not substitute a generic command that the project does not run.
- Identify generated and vendored paths, then leave them untouched.
- Record the selected rule sources and revisions in the standards brief.

- Make the smallest coherent change that satisfies the accepted criteria.
- Preserve public behavior, interfaces, data formats, and error contracts unless
  the slice explicitly changes them.
- Match the local naming, package layout, error type, and logging style.
- Prefer deletion and reuse over new abstraction. Do not add a layer for a single
  call site.
- Do not upgrade dependencies, reformat unrelated files, or migrate tooling as a
  side effect.

- Validate untrusted input at the boundary where the project expects it.

  client-provided scope or ordering decision.

  code, fixtures, logs, and shared references.

# Java Project Standards

Read the project's build files and `AGENTS.md` first. Use the JDK, framework,
formatter, linter, and dependency versions the project already declares; this
reference does not prescribe an upgrade or a default stack.

## Baseline

- Confirm the compiler release and any toolchain configuration before using newer
  language features.
- Follow the project's formatter/linter configuration. Do not reformat unrelated
  code.
- Keep package layout, visibility, and naming consistent with nearby code.
- Do not add a dependency when the JDK or an existing library covers the need.
- Leave generated sources and generated SQL/mapper artifacts untouched unless the
  slice owns their source of truth.

## Persistence Boundaries

- Use the persistence technology already present. Do not default to JPA, and do
  not add an extra Repository layer when the project queries its mapper or
  existing boundary directly.
- When MyBatis-Plus is present, read `spring-mybatis-plus.md`; it is the authority
  for wrappers, partial updates, pagination, logical delete, and SQL fragments.
- Keep database constraints and migrations consistent with the code. A service
  check does not replace a unique or foreign-key constraint when one is possible.

## Types, Nulls, And Errors

- Prefer explicit types at API boundaries; avoid raw collections and `null`
  returns that callers cannot distinguish from absence.
- Treat nullable columns and wrapper types deliberately. Do not silently convert
  missing data to `0`, `""`, or a default timestamp.
- Throw the project's domain or framework exception with context. Do not catch an
  exception and continue as if the operation succeeded.
- Do not log secrets, full request bodies, credentials, or personal data.
- Preserve exception contracts that callers and transactions rely on.

## Concurrency And Transactions

- Do not add a lock or a synchronized block without a stated contention scenario,
  ownership rule, timeout, and failure path.
- Prefer database constraints, optimistic versions, and short transactions over
  process-wide locks.
- Keep remote calls, file I/O, and user interaction out of a transaction when the
  project allows it.
- Test the claimed behavior with a real or project-approved database when the
  slice changes transactional, locking, or constraint behavior.

## Tests

- Use the project's existing test framework, naming, fixtures, and database
  strategy.
- Assert observable behavior rather than implementation wiring.
- For persistence changes, include evidence of the generated SQL or database
  result when the slice changes query or update semantics; otherwise state why
  that evidence is unavailable.
- Run the project's formatter, compiler, and focused tests; report the exact
  commands and outcomes.

# Spring + MyBatis-Plus Standards

Use this reference only when the project already uses Spring and MyBatis-Plus.
Read the project's MyBatis-Plus version, Spring Boot version, JDK, migrations,
and existing mapper style first. The project's version and configuration win.
Official references:

- Wrapper and condition construction: <https://baomidou.com/en/guides/wrapper/>
- Block-attack plugin: <https://baomidou.com/plugins/block-attack/>

Do not introduce JPA, an extra Repository layer, a new plugin, or a dependency
upgrade to satisfy this reference.

## Trusted Query Scope

- Build wrappers from backend-controlled fields. Never concatenate a request
  parameter into SQL text, a column name, an `orderBy`, an `apply` fragment, or
  `last`.
- `${}` substitutes text directly and is an injection risk; `#{}` binds a
  parameter. Use parameter binding for every value.
- `{0}` inside wrapper fragments such as `apply` is still a bound parameter
  placeholder, not string interpolation. Keep the fragment itself constant and
  backend-controlled; `apply("date_format(created_at,'%Y-%m-%d') = {0}", day)` is
  acceptable only when the expression is fixed and `day` is bound.
- `last` appends a raw final SQL segment. Use it only for a constant,
  backend-controlled clause that cannot be expressed otherwise. Never pass user
  input, and never use it to append `;` or a second statement.
- Use lambda wrappers or explicit column constants so a renamed field fails at
  compile time. Whitelist sortable/filterable columns instead of accepting client
  names.
- Keep tenant, organization, and data-scope predicates in the backend. Do not
  offer a client toggle that removes them.
- Select only needed columns for wide tables or read paths; avoid `SELECT *` when
  the project already uses explicit projections.

## Partial Updates And Null Semantics

- `updateById` and entity-based updates skip `null` fields under the default
  field strategy. That is useful for partial updates but cannot clear a column.
- To set a column to SQL `NULL`, use an explicit update wrapper such as
  `update(null, Wrappers.<Entity>lambdaUpdate().eq(Entity::getId, id).set(Entity::getNote, null))`

- Field-level `@TableField(updateStrategy = FieldStrategy.ALWAYS)` is acceptable

- Include the intended optimistic version or update predicate in the `WHERE`

## SQL Fragments And Reuse

- Keep reusable fragments small and parameterized. A fragment that accepts raw
  column names or ordering is not reusable safely.
- Do not move business authorization into a shared fragment that callers can
  bypass.
- Prefer wrapper composition over string concatenation. If XML is the project's
  convention, follow its namespace, result-map, and parameter conventions.
- Check generated SQL in a test or project logging when a wrapper becomes
  non-trivial.

- Use MyBatis-Plus pagination (`Page`/`IPage`) with the project's configured
  `PaginationInnerInterceptor`; do not hand-build `LIMIT` from request values.
- Set and verify a maximum page size, overflow behavior, and a deterministic
  order. Unordered pagination is not stable evidence.
- Treat total-count queries as potentially expensive; use the project's count
  optimization or a separate count only when the existing configuration supports
  it.
- Test the first page, a middle page, the last/empty page, and an oversized page
  request when the slice changes list behavior.

## Audit And Logical Delete

- Follow the project's existing `@TableLogic`/logic-delete field. Reads, updates,
  and uniqueness rules must account for the deleted marker.
- Understand whether unique indexes include the delete marker; a logical delete
  can otherwise block re-creation. Prefer a database constraint that matches the
  intended behavior.
- Use the framework's delete methods or an explicit wrapper. Do not bypass logical
  delete with raw SQL unless the slice explicitly owns a restore/purge operation.
- Record audit timestamps/operators through the project's fill mechanism, and
  verify custom updates that bypass entity fill.
- A purge or restore path needs its own authorization, audit, and transaction
  evidence; it is not a normal delete.

## Transactions And Concurrency

- Put `@Transactional` on the public service boundary that owns the unit of work.
  Remember that self-invocation bypasses the proxy; move the call to another bean
  or use the project's established pattern.
- Declare rollback behavior for checked exceptions when the project relies on it.
  Do not swallow an exception and commit a partial write.
- Keep transactions short; avoid remote calls, file I/O, and waits inside them
  when the project permits.
- Prefer a unique constraint and a narrow update predicate for races. Use
  `@Version` with `OptimisticLockerInnerInterceptor` only when the table already
  has a version column and the project uses that pattern; handle the zero-row
  update as a conflict.
- Do not add process-wide, distributed, or table locks by default. A lock needs a
  named contention scenario, timeout, ownership rule, and failure behavior.
- Do not add the block-attack plugin or another interceptor as a blanket policy.
  If the project already uses it, keep it configured; if the slice needs
  full-table update/delete protection, treat that as a scoped project decision
  with tests.

## Verification And Database Evidence

  `UNVERIFIED` instead of inferring it from a mock.

- Capture actual SQL or database state only with project-approved logging. Do not
