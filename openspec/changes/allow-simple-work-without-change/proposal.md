# 提案：简单工作免建 OpenSpec 任务

## 目标
对需求明确、非行为性、局部且低风险的小改动，允许直接执行并在对话中交代验证；不再为每个请求强制发现、新建或复用 OpenSpec change。正式变更仍由 OpenSpec 唯一持有持久任务状态。

## 范围内
- 主路由在 OpenSpec discovery 前判断快速通道；唯一资格源位于 `references/quality-profiles.md`。
- 文档、文案、格式和不改变行为的局部配置/代码整理，可在主会话直接执行。
- 需求明确、可在当前会话完成，无正式计划、跨会话交接、委派或持久记录要求；不属于当前选定 change 的继续工作。
- 快速通道只省任务记录及正式阶段，不省 diff 检查和项目要求的最小相关验证。
- 正式模式的匹配确认、TDD、审核预算、验收归档和 legacy 保护不变。
- 同步主路由、共享治理、命令、规划/收尾入口、使用文档与测试场景。

## 范围外
- 正常行为变更、bug fix、重构；安全、权限、资金、密钥、持久数据、迁移、公共合同、依赖变更、破坏性操作。
- 修改 OpenSpec CLI、外部 OMP gate、注入器或上游技能；新增调度引擎、配置开关、任务状态文件。
- 把未安装/故障的 CLI 当作降级理由；自动修改本机全局安装、提交、推送、验收或归档。

## 用户确认与假设
- 用户于本轮选择“先覆盖非行为性小改动（推荐）”以及“创建并实施（推荐）”，明确授权本 change 的创建及按该边界实施。
- 当前仓库根和 CLI 已存在；通过现有 `create_change` 创建本记录，没有初始化新根。
- 现有未提交的其他 change 归档移动、生成副本与 legacy 文件不是本 change 的交付范围。
- 静态合同测试及场景资产可证明规则一致，不能证明四宿主运行时必然遵守；实际新会话演练另行列为未运行。

## 验收标准
- [ ] AC-001：主路由在任何 discovery/建档前应用共享资格源；符合条件的小改动直接进入快速执行，不因现有 `openspec/`、CLI 缺失或无关候选而先匹配任务。
- [ ] AC-002：快速通道无需新建/复用确认，不创建/更新 OpenSpec、`.workflow/`、`.trellis/` 或替代任务状态；在主会话执行，省略正式规划、委派和默认独立审核。
- [ ] AC-003：执行后检查相关 diff，运行最小相关且项目要求的验证，直接报告真实结果、未运行项和风险；不伪造 `CLEAN` 或回补 formal artifacts。
- [ ] AC-004：行为/风险/范围不符、显式 OpenSpec 或选定 change 续接、正式计划/交接/委派要求及项目更严格规则均走正式模式；快速执行中发现上述情况时停止扩大实现，保留现有差异和检查，再按原匹配确认规则升级。CLI 错误不使不合格任务获得快速资格。
- [ ] AC-005：命令和面向人的流程图与主路由一致；规划/收尾入口能识别已选快速通道并返回主路由/对话收尾，不反向强制创建 proposal、tasks 或 verification；正式模式仍保留其原有要求。
- [ ] AC-006：新增测试先 RED 后 GREEN；全套合同/Python及严格 OpenSpec 校验通过，隔离和本项目 All 安装内容一致；执行一次独立完整审核，记录限制并停在 `awaiting-acceptance`。

## 影响
- 修改现有技能和文档，不增加依赖或新安装单元。
- 变更既有“所有请求先 discovery”的入口合同，保留其正式分支；已有 OpenSpec change 不迁移、不删除。
- 新增能力 `simple-work-routing`，不将历史 active change 自动复用到新的简单请求。
