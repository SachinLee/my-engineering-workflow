# 设计

## 背景

见 `proposal.md` 的 Why。`skills/run-engineering-workflow/references/workflow-governance.md` 已有证据门槛；本变更只把“删掉候选机制会不会违反具体要求”的反事实判断显式化。`skills/plan-solution/SKILL.md` 已要求审查额外机制，并引用共享治理规则。

## 目标 / 非目标

**目标：** 让各端复用同一条短规划规则；给有意调整规划提示的人提供一次可复现、可盲评的小样本对照。

**非目标：** 改 GPT/供应商或各 agent 模型配置；新增自动 LLM runner、agent、MCP、运行时 gate；要求普通任务执行消融；删除任何已要求或必要的保护。

## 决策

1. 在 canonical `workflow-governance.md` 的 Evidence-Based Planning 中增加一条简短反事实判据，并在 `plan-solution` 现有“审查设计机制”步骤明确引用。优先让所有宿主复用共同规则，不在 Codex、Pi、OpenCode、Claude Code 的 agent 模板各复制一份。
2. 通过一个 `node:test` 合同测试验证规则确实存在于 canonical 共享指导、且没有把普通错误处理变成逐行清单。使用现有 `npm test`，不新增测试依赖。
3. 新增 10 个合成案例（简单、普通、高风险），作为一次性评估输入；不包含用户私有历史。维护手工协议而非通用评测程序。A/B 仅相差新增的反事实规则，模型、案例、上下文和工具固定，生成会话独立，评分盲化。
4. 评分看无依据的新增机制、AC/必要不变量覆盖、可验证性和实现工作量；“无依据机制在多数案例减少且必要覆盖零回退”才算正向信号。篇幅/token 不作成功指标。任何安全/授权/数据完整性保护只做方案反事实，不在生产移除。
5. 试点若因无法确认有效模型、隔离条件或盲评而未运行，结果如实标为 `NOT RUN`；不得把文档和合同测试说成提示效果证据。

## 风险与取舍

- [案例过于合成] → 结果只作为方向性试点，并记录样本限制；不宣称统计显著。
- [A/B条件漂移] → 两臂使用同一冻结的案例、模型与工具；候选臂只增加一条规则；保存评分前的匿名化输出和实际可确认的模型信息。
- [规则重复已有治理] → 只加最短的反事实判据，并复用现有 evidence 门槛，不再创建章节模板或多个 agent 检查点。

## 发布与回滚

先通过合同测试和 `npm test`，再按协议运行一次试点并记录结果。回滚只需删除新增的短规则、对应测试及评估材料；不改外部 agent 配置或用户数据。
